## Why

People rarely learn about things at the moment they happen. A report entered on Friday about something that happened on Monday has Monday as its event time and Friday as its entry time; a prediction entered on Monday about Friday has them the other way around. Keeping both lets readers tell what was expected in advance from what was learned afterward, and reconstruct what was known at any moment.

## Done when

- Unit tests cover the equality boundaries of Past and Future, both edges of the Real-time delay, timestamp normalization, and whole-second precision.
- A file that claims or changes `entered_at` or `entry_timing` is rejected.
- Changing a type's rule in `timeline.yaml` does not change how already-recorded events are judged.
- An open event becomes past due as the clock passes its date.

## Why it will work

The entry time comes only from the clock at the moment of recording, never from the author, a dry run, or a file timestamp, so it cannot be backdated by mistake. Once recorded, the rule is frozen in the event's own file.

## Design

### Timing rules

| Rule | Meaning | Example |
| --- | --- | --- |
| Past | The event happened before it was entered | News: something happened, and we learn about it now |
| Future | The event was entered before it happens | A prediction, a goal, or a task due later |
| Real-time | The event was entered as it happened | A live observation, within the type's allowed reporting delay |

Let E be the event time and A the entry time.

- `past`: E < A
- `future`: E > A
- `real_time`: 0 <= A - E <= `max_delay`

A Real-time type defines how much delay it accepts, so an old observation cannot appear live just because it was entered now. Timeline checks timing and required information; it does not decide whether a claim is true.

### Entry time

A draft is validated as if it were recorded now, so a Future draft whose date has already passed fails: it can no longer be entered in advance. Record plans before their dates, or move the date.

For a new event, A is the time the check records it, read from an injected clock after validation succeeds and immediately before writing; never the command's start time, a dry run, a file timestamp, or a value in draft YAML.

`entry_timing` is written into the file at first recording so a reader of the file alone can see whether the event was entered after, before, or as it happened. It is written once, from the type's rule at that moment, and is the authoritative rule for the event from then on: if the type's rule in `timeline.yaml` changes later, the event keeps the rule it was entered under.

### IDs and timestamps

- IDs are [ULIDs](https://github.com/ulid/spec): they sort by creation time and can be generated by independent writers without coordination.
- Timestamps are RFC 3339 with an explicit offset and whole-second precision. Comparisons use UTC. `entered_at` is written in UTC with a `Z` suffix.

### Updates

The timing rule describes an event when it is first entered and does not change as the clock moves: a prediction entered in advance remains one after its date passes. An update is checked against the event's original entry time and the rule in its `entry_timing` field. Its fields are validated against the current type definition, so types can gain fields over time. Unchanged events are never revalidated. Changing an event's type and restoring a removed event are not supported initially.

### Past due

Where an event sits relative to now (past, upcoming, past due) is computed at read time and is separate from its entry timing rule. An event is **past due** when its type has `status`, its status is not closed, and its event time is before now. Past due is computed from the injected clock and never stored. It is not an error: the event stays valid and visible until someone closes it or moves its date. Moving a date is an ordinary edit; for a Future event the new date must still be after the original `entered_at`. Keeping a record of every slip is part of the [record store](primary-goal-build-timeline.md#later-directions).
